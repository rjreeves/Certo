# Certo language manual: SDL, MDL and QL

Certo has three small languages that work together:

| Language | What it is for | File |
|----------|----------------|------|
| **SDL** (schema definition language) | Declares the schema: tables, columns, enums, keys, indexes, constraints and simple views. | `schema.sdl` |
| **MDL** (migration directives) | Says what a schema change *means* when the difference alone cannot tell: a rename, a removed enum value, a value to backfill, a step to run. | `migration.mdl`, one per migration, optional |
| **QL** (query language) | Typed queries and mutations, and richer views, checked against the schema. Every statement compiles to SQL for PostgreSQL, SQLite or MySQL, plus a typed contract. | `queries.ql`, `views.ql` |

You write SDL; Certo compares it with the schema it had before and produces a **migration** (SQL for your database). You write QL; Certo checks it against the schema, tells you the type and nullability of every parameter and result column, lowers it to SQL, and can generate host code (C# or Rust) from it.

This manual is the reference for the three languages. For how to run things (`certo migrate`, `certo ql run`, ...) see the [CLI manual](https://github.com/rjreeves/certo-cli/blob/main/docs/cli-manual.md); for using Certo from code see the [developer guide](developer-guide.md).

**Design rule.** Certo only offers behaviour that is identical on every database it supports. Where PostgreSQL, SQLite and MySQL disagree, the feature is either made to agree or refused with a reason (a numbered diagnostic). Section 6 lists what differs between the databases.

## Conventions used here

- Code blocks tagged `sdl`, `ql` and `mdl` are complete and have been checked by Certo against the example schema below; blocks tagged `text` show output.
- `//` starts a comment in all three languages. Keywords are *contextual*: `key`, `one`, `many`, `status` and similar words stay legal as column names.
- Names are case-sensitive. Statement, table, column and alias names are identifiers: a letter, then letters, digits and `_`.

## The example schema

The examples in this manual use a small shop. It is shown in full here and used in every QL example.

<!-- shop -->
```sdl
enum OrderStatus { new, paid, shipped }

table customers {
    id: serial primary key
    name: varchar(80) not null
    email: varchar(120) unique
    born: date
    balance: decimal(10,2)
    meta: json
}

table orders {
    id: serial primary key
    customer_id: int not null references customers on delete cascade
    status: OrderStatus not null default new
    total: decimal(10,2) not null
    qty: smallint not null default 1
    paid: bool not null default false
    note: text
    created: timestamp not null default now()
    shipped: timestamp
}

table items {
    id: bigserial primary key
    order_id: int not null references orders
    sku: varchar(40) not null
    price: decimal(10,2) not null
}

table categories {
    id: serial primary key
    parent_id: int references categories
    name: varchar(60) not null
}

index orders_status on orders (status)
constraint total_positive on orders using total >= 0
```

# 1. SDL: the schema

A schema file is a list of declarations in any order: `table`, `enum`, `type`, `sequence`, `index`, `constraint` and `view`. Tables, enums, composite types, sequences and views share one namespace: no two may have the same name, and none may be named like a builtin type.

## 1.1 Tables and columns

```sdl
table people {
    id: serial primary key
    name: text not null
    nickname: text
}
```

A column is `name: type` followed by any of these modifiers, in any order:

| Modifier | Meaning |
|----------|---------|
| `primary key` | The column is (part of) the primary key. Several columns can be marked: the key is composite. A key column is never null. |
| `unique` | The values are unique. |
| `not null` | The column cannot hold NULL. Without it a column is nullable. |
| `null` | Says explicitly that it is nullable (the default). |
| `default <expression>` | The value used when an insert gives none. See 1.5. |
| `generated always` / `generated by default` | An identity column: see 1.4. |
| `references Table [(column)] [on delete <action>] [on update <action>]` | A foreign key: see 1.6. |

A table with no primary key compiles with a warning.

## 1.2 Types

| SDL type | Meaning | PostgreSQL | SQLite | MySQL |
|----------|---------|------------|--------|-------|
| `text` | Text of any length | `text` | `TEXT` | `LONGTEXT` |
| `varchar(n)` | Text up to `n` characters | `character varying(n)` | `VARCHAR(n)` | `VARCHAR(n)` |
| `char(n)` | Fixed-length text | `character(n)` | `CHAR(n)` | `CHAR(n)` |
| `smallint`, `int`, `bigint` | Whole numbers (16, 32, 64 bit) | same | `SMALLINT`, `INTEGER`, `BIGINT` | `SMALLINT`, `INT`, `BIGINT` |
| `decimal(p, s)` (also `numeric`) | Exact decimal number | `numeric(p,s)` | `NUMERIC(p,s)` | `DECIMAL(p,s)` |
| `decimal` | Exact decimal, unconstrained | `numeric` | `NUMERIC` | `DECIMAL(65,30)` |
| `real`, `float` | Floating point (32, 64 bit) | `real`, `double precision` | `REAL`, `DOUBLE` | `FLOAT`, `DOUBLE` |
| `bool` | true or false | `boolean` | `BOOLEAN` | `BOOLEAN` |
| `uuid` | A UUID | `uuid` | text | `CHAR(36)` |
| `timestamp` | A point in time (UTC) | `timestamptz` | text | `DATETIME(6)` holding UTC |
| `timestamp_naive` | A date and time without a zone | `timestamp` | text | `DATETIME(6)` |
| `date` | A calendar date | `date` | text | `DATE` |
| `json` | A JSON document | `jsonb` | text | `JSON` |
| `bytes` | Binary data | `bytea` | `BLOB` | `LONGBLOB` |
| an enum name | One of the enum's values | an enum type | text with a CHECK | an inline `ENUM(...)` |
| a composite type name | A record of fields | a composite type | not available | not available |

`decimal(precision)` means scale 0. Only `varchar`, `char` and `decimal` take parameters. `timestamp`, `timestamp_naive` and `date` convert into one another, so `now()` is a valid default for a plain `timestamp_naive`.

## 1.3 Enums

```sdl
enum Role { admin, user, guest }

table accounts {
    id: serial primary key
    role: Role not null default user
}
```

An enum is a closed set of names. A column of an enum type holds exactly one of them; a default is written as the bare value (`default user`), and in queries as a string (`"admin"`) that Certo checks against the enum's values.

Adding a value is a normal migration. **Removing** a value needs an MDL `remap` directive saying where the rows with that value go (see section 2).

## 1.4 Auto-generated columns

- `serial`, `bigserial` and `smallserial` are spellings of an integer column (`int`, `bigint`, `smallint`) whose value is generated by a counter the column owns.
- `generated always` and `generated by default` make an integer column a SQL-standard identity column. (`always` refuses explicit values; MySQL cannot enforce that, so there it is refused with a message.)

All three imply `not null`, cannot have another default, and only apply to integer columns of a table. In the schema they are a property of the column, not a type, so a serial key is an `int` column and `author_id: int references users` needs no special case.

## 1.5 Defaults and expressions

A default, a `constraint` and a view's `where` use the same small expression language:

- **Literals:** strings in double quotes (`"hello"`), whole numbers (`-5`), decimals (`1.50`, kept exactly as written), `true` and `false`.
- **Names:** a column of the same table (in constraints and view conditions) or an enum value (in an enum column's default).
- **Operators**, loosest to tightest: `or`; `and`; `not`; comparison (`==` `!=` `<` `<=` `>` `>=`, `is [not] null`, `[not] in (...)`); `+` `-`; `*` `/`. Binary operators group left to right. `is null` and `in` sit at the comparison level, so write `a == (b is null)` with parentheses.
- **Functions:**

| Function | Result |
|----------|--------|
| `now()`, `today()`, `gen_uuid()` | the current timestamp, the current date, a random v4 UUID |
| `lower(t)`, `upper(t)`, `trim(t)` | text |
| `substr(t, start [, len])`, `replace(t, from, to)`, `left(t, n)`, `right(t, n)` | text (`start`, `len`, `n` are whole-number literals) |
| `starts_with(t, prefix)` | bool |
| `length(t)`, `position(t, find)` | int (`position` is 1-based, 0 if absent) |
| `add_days(date, n)`, `days_between(from, to)` | date, int |
| `date_part("year"\|"month"\|"day"\|"hour"\|"minute", x)` | int |
| `abs(n)`, `round(n)` | same type |
| `coalesce(a, b, ...)`, `nullif(a, b)` | the type of `a` |
| `is_null(x)` | bool, same as `x is null` |
| `nextval(sequence)` | bigint (PostgreSQL only) |

Limits keep the compiler safe on small stacks: at most 500 elements, 128 levels of depth and 64 levels of nesting per expression.

## 1.6 Foreign keys

```sdl
table users {
    id: serial primary key
}

table posts {
    id: serial primary key
    author: int not null references users on delete cascade
    editor: int references users on delete set null
}
```

`references Table` points at that table's single-column primary key (or a named unique column: `references Table(column)`). The column's type must match. `on delete` and `on update` take `cascade`, `restrict`, `set null` or `no action` (the default). `set null` needs a nullable column.

## 1.7 Indexes and constraints

```sdl-fragment
index orders_status on orders (status)
index orders_customer_created on orders (customer_id, created)
constraint total_positive on orders using total >= 0
constraint paid_has_total on orders using not paid or total > 0
```

An index lists one or more columns of one table. A `constraint` is a CHECK: a boolean expression over that table's columns. Index and constraint names are unique across the whole schema (not just per table). On MySQL, a `text`, `json` or `bytes` column cannot be indexed or `unique`: use `varchar(n)`.

## 1.8 Composite types and sequences (PostgreSQL)

```sdl-fragment
type Address { street: text  city: text  zip: varchar(10) }

sequence order_seq start 1000 increment 5

table shipments {
    id: bigint primary key default nextval(order_seq)
    to: Address
}
```

A `type` is a record of fields (no `serial`, and it cannot contain itself). A `sequence` is a counter shared across columns or tables (use `serial` for a column's own counter); its options `start`, `increment`, `min`, `max`, `cache` and `cycle` take PostgreSQL's defaults when left out. SQLite and MySQL have neither: a migration that needs one is refused with a message that says which.

## 1.9 Views

```sdl
table people {
    id: serial primary key
    name: text not null
    age: int
}

view adults on people (id, name) where age >= 18
view everyone on people (id, name, age)
```

A view in SDL reads **one table**: it picks some of its columns and, optionally, only the rows a condition keeps. It is part of the schema, so migrations create, change and drop it, and it is read back from a database when you import or adopt one. A view is read-only, and QL queries read it like a table.

Anything richer (joins, grouping, ordering, another view) belongs in a QL view: see 3.15.

## 1.10 Names and namespaces

- A name starts with a letter and continues with letters, digits and `_`.
- Tables, views, enums, composite types and sequences share one namespace.
- Index and constraint names are each unique across the schema.
- A name cannot be a builtin type name (`text`, `int`, `date`, ...).

## 1.11 SDL diagnostics

Diagnostics print as `file:line:column: error CODE: message`. The main ones:

| Code | Meaning |
|------|---------|
| `SDL100` | Syntax error (expected something else). |
| `SDL101` | An expression is nested too deeply. |
| `SDL200` | A name is already declared, or is a builtin type. |
| `SDL202` | A type name is unknown, or names a table, view or sequence. |
| `SDL204`, `SDL205` | A duplicate enum value or composite field. |
| `SDL206` | A table or column does not exist (also in an index or view). |
| `SDL208` | An unknown name in an expression. |
| `SDL211` | A constraint or view condition is not boolean. |
| `SDL212` | A composite type contains itself. |
| `SDL213` | A view reads something that is not a table. |
| `SDL230`-`SDL233` | A bad foreign key: missing target, type mismatch, a non-unique target, `set null` on a not-null column. |

# 2. MDL: migration directives

When you change `schema.sdl`, Certo diffs it against the previous schema. A diff alone cannot tell a **rename** from a drop plus an add, and it cannot know where rows with a removed enum value should go. An MDL file states that intent. It never restates the schema.

You pass an MDL file when creating a migration: `certo migrate new <name> --mdl file.mdl`. Its directives apply to that one migration.

## 2.1 Renames

```mdl
rename table users -> accounts
rename column accounts.nick -> username
```

`rename table old -> new` keeps the data. `rename column table.old -> new` names the **old** table (its name before this migration, so after a table rename in the same file, use the old name) and the old column. A rename must remove the old name: if the new schema still has it, the directive is refused.

## 2.2 Removing an enum value

```mdl
remap Role.guest -> user
```

Rows holding `guest` become `user`, then the value is removed. Without a `remap`, removing an enum value is refused (PostgreSQL cannot drop a value; SQLite and MySQL could lose data).

## 2.3 Backfilling a new NOT NULL column

```mdl
backfill customers.display_name = name
```

Fills the column for existing rows (from an expression over the **new** schema's columns) before it is made `not null`. It is safe by construction, so it does not count as destructive.

## 2.4 Steps before and after

```mdl
before { update users set age = 18 where is_null(age) }
after  { sql postgres "ANALYZE users"  sql "SELECT 1" }
```

A `before` block runs first and sees the **old** schema; an `after` block runs last and sees the **new** one. A step is:

- `update <table> set <column> = <expr> [, ...] [where <expr>]`, written in SDL expressions; or
- `sql [dialect] "<raw SQL>"`, where the dialect is `postgres`, `sqlite` or `mysql`; with no dialect the SQL runs on every database.

Raw SQL and data updates make a migration **destructive** in Certo's sense (it can change or lose data), so `certo migrate new` asks for `--allow-destructive`.

## 2.5 What counts as destructive

`certo migrate new` refuses a plan that can lose data unless you pass `--allow-destructive`. That covers dropping a table, column, enum, type or sequence; removing an enum value; narrowing a type (for example `int` to `smallint`), making a column `not null` or `unique` where existing rows may break it; and any data update or raw SQL step. Widening changes (`smallint` to `int`, a longer `varchar`) are not destructive.

## 2.6 MDL diagnostics

| Code | Meaning |
|------|---------|
| `MDL303` | A rename names something that still exists in the new schema (the old name must go). |
| `MDL304` | A table or column is part of more than one rename. |
| `MDL315` | Unknown SQL dialect in a `sql` step (use `postgres`, `sqlite` or `mysql`). |
| `MDL316` | A `sql` step is empty. |
| `MDL320` | A `backfill` has no effect: the migration neither adds the column as NOT NULL nor makes it NOT NULL. |

# 3. QL: queries and mutations

A QL file holds named, parameterised statements. Every statement is checked against the schema and compiles to SQL **and** a typed contract: the type and nullability of each result column and each parameter.

There are two kinds of statement: **queries** (read) and **mutations** (`insert`, `update`, `delete`). There are also **fragments** and **views** (3.14, 3.15).

## 3.1 A first query

```ql
query big_orders(min_total: decimal(10,2)) {
    from orders o
    join customers c on o.customer_id == c.id
    where o.total >= :min_total
    select c.name, o.total
    order by o.total desc
    limit 10
}
```

- `query name(parameters) { ... }` declares the statement. Parameters are `name: type`; add `null` after the type (`since: date null`) to allow NULL. Types are SDL's: `int`, `text`, `decimal(10,2)`, an enum name, ...
- Clauses come in a **fixed order**: `from`, joins, `where`, `group by`, `having`, `window`, `select`, then `order by`, `limit`, `offset`.
- A parameter is used as `:name`.
- Tables are given a short alias (`from orders o`). The alias defaults to the table's name.

`certo ql check` prints the contract:

```text
query big_orders(min_total: decimal(10,2))
  -> name varchar(80), total decimal(10,2)
```

## 3.2 Tables, aliases and joins

```ql
query orders_with_customer() {
    from orders o
    join customers c on o.customer_id == c.id
    left join items i on i.order_id == o.id
    select o.id as order_id, c.name, i.sku
}
```

`join` (same as `inner join`) and `left join` take an `on` condition. A column is written `alias.column`, or just `column` when only one table has it. A **left join makes the far side's columns nullable** in the result: `i.sku` above is `varchar(40)?`.

## 3.3 Selecting

```ql
query some_columns() {
    from customers c
    select c.id, upper(c.name) as shout, c.balance * 2 as double_balance
}

query everything() { from orders o select * }

query distinct_status() { from orders o select distinct o.status }
```

Every selected item needs a name: a plain column keeps its name; anything else needs `as name` (QL215). Names must be unique in the result (QL216). `select *` and `select o.*` expand to the table's columns.

## 3.4 Filtering

```ql
query filtered(from_date: date, who: text null) {
    from customers c
    where c.born >= :from_date
      and (:who is null or c.name like :who)
      and c.balance between 0 and 1000
      and c.meta is not null
      and c.name not in ("root", "admin")
    select c.id
}
```

Available tests: `==` (or `=`), `!=` (or `<>`), `<`, `<=`, `>`, `>=`, `is [not] null`, `[not] in (list)`, `[not] like pattern`, `[not] between a and b`, `and`, `or`, `not`. A string compared with an enum column is checked against the enum's values (QL218); a string may also stand for a uuid, date or timestamp value.

`null` is a literal too (`where c.born == null` is not what you want: use `is null`).

## 3.5 Grouping and aggregates

```ql
query spending() {
    from customers c
    join orders o on o.customer_id == c.id
    group by c.id, c.name
    having count(*) >= 2
    select c.name, count(*) as orders, sum(o.total) as spent, max(o.created) as last_order
    order by spent desc
}
```

Aggregates: `count(*)`, `count([distinct] x)`, `sum`, `avg`, `min`, `max`, and `string_agg` (3.10). They are allowed only in `select`, `having` and `order by`, and cannot nest (QL213). Once there is a `group by` or an aggregate, every selected column must be grouped or used inside an aggregate (QL214).

`sum`, `avg`, `min` and `max` can be NULL (an empty group), so their result columns are nullable; `count` never is.

## 3.6 Ordering, limit and offset

```ql
query page(page: int, size: int) {
    from orders o
    select o.id, o.total
    order by o.created desc, o.id
    limit :size offset :page
}
```

`order by` takes expressions, each `asc` (default) or `desc`, and may name an output column. `limit` and `offset` take a non-negative whole number or an integer parameter. With `select distinct`, `order by` must use selected columns (QL221).

## 3.7 Expressions

| Kind | Examples |
|------|----------|
| Arithmetic | `o.total * 1.2`, `o.qty + 1`, `a - b`, `a / b` (on whole numbers `/` is integer division) |
| Concatenation | `c.name \|\| " <" \|\| c.email \|\| ">"` joins text end to end; NULL if any part is |
| Case | `case when o.paid then "paid" when o.total > 100 then "big" else "small" end` |
| Text | `lower`, `upper`, `trim`, `substr(s, 1, 3)`, `replace`, `left(s, 2)`, `right(s, 2)`, `starts_with`, `length`, `position` |
| Dates | `now()`, `today()`, `add_days(d, 7)`, `days_between(a, b)`, `date_part("year", d)` |
| Numbers | `abs`, `round` |
| Null handling | `coalesce(a, b, ...)`, `nullif(a, b)` |

Types follow SDL's rules: numbers mix, text-like types mix, dates and timestamps mix; anything else is an error (QL211). A `case` without `else` is nullable. `||` needs at least one text operand and refuses decimals, bools, dates, timestamps, json and bytes (QL257), because their text differs between databases.

## 3.8 Subqueries

```ql
query with_subqueries() {
    from customers c
    where c.id in (from orders o where o.paid select o.customer_id)
      and exists (from orders o where o.customer_id == c.id and o.total > 100 select o.id)
    select c.name,
           (from orders o where o.customer_id == c.id select max(o.total)) as biggest
}
```

A subquery is a query's own clauses in parentheses. It may use the tables of the queries around it (correlation); its own names win. `in (...)` and a scalar subquery need exactly one column (QL240); a subquery used as a value must yield at most one row (QL241): use an aggregate or `limit 1`. Subqueries nest six deep (QL243).

## 3.9 `with` queries and recursion

```ql
query top_customers() {
    with spend as (
        from orders o group by o.customer_id select o.customer_id, sum(o.total) as total
    )
    from customers c join spend s on s.customer_id == c.id
    select c.name, s.total
    order by s.total desc
    limit 5
}

query category_tree() {
    with recursive tree as (
        from categories c where c.parent_id is null select c.id, c.name, 0 as depth
        union all
        from categories c join tree t on c.parent_id == t.id select c.id, c.name, t.depth + 1 as depth
    )
    from tree t select t.name, t.depth order by t.depth, t.name
}
```

`with name as (query)` names a query and lets the body use it like a table; its columns are the select list's names and types. A recursive query is a start select joined by `union` or `union all` to steps that read the query itself exactly once; the columns come from the start, so write literals that match (`0` for an integer depth). `union all` on a cyclic graph never ends: bound it with a depth column, or use `union`. `with` may also start an `insert`, `update` or `delete`.

## 3.10 Set operations, windows, filters and JSON

**Set operations** combine queries with the same number of compatible columns:

```ql
query all_names() {
    from customers c select c.name
    union
    from categories g select g.name
    order by name
}
```

`union [all]`, `intersect` and `except` (no `all` for the last two). One query uses only one of the three kinds (QL253). `order by`, `limit` and `offset` come after the last branch and may only name output columns (QL250).

**Window functions** compute over a set of rows without collapsing them:

```ql
query ranked() {
    from orders o
    window w as (partition by o.customer_id order by o.created)
    select o.id,
           row_number() over (partition by o.customer_id order by o.total desc) as rn,
           sum(o.total) over (partition by o.customer_id) as customer_total,
           lag(o.total, 1, 0) over w as previous
    order by o.id
}
```

Available: the aggregates (`count`, `sum`, `avg`, `min`, `max`), `row_number`, `rank`, `dense_rank`, `ntile(n)`, `percent_rank`, `cume_dist`, `lag`/`lead`, `first_value`, `last_value`. A frame limits the rows seen: `sum(x) over (order by id rows between 2 preceding and current row)`. Frames use `rows`, `range` or `groups` (`groups` is not available on MySQL, QL271); see the grammar for the bounds. A named `window w as (...)` is defined before `select` and used with `over w`.

**Filtered aggregates** and **`string_agg`**:

```ql
query paid_stats() {
    from orders o
    select count(*) as all_orders,
           count(*) filter (where o.paid) as paid_orders,
           string_agg(o.note, ", ") as notes
}
```

`count(*) filter (where cond)` counts only matching rows (any aggregate takes `filter`). `string_agg(text, "sep" [order by ...])` joins values, skipping NULLs; it needs a text argument, the separator is a literal and the result is NULL for an empty group.

**JSON values.** `json_text(j, "key", ...)`, `json_int`, `json_bool` and `json_has` read a `json` column along a literal path of one to four keys (names or array positions):

```ql
query plans() {
    from customers c
    select c.name,
           json_text(c.meta, "plan") as plan,
           json_int(c.meta, "limits", "seats") as seats,
           json_bool(c.meta, "trial") as trial,
           json_has(c.meta, "tags", 0) as tagged
}
```

Each returns only what every database agrees on: a JSON string as text, a whole number below 10^18 as `bigint`, `true`/`false` as a boolean; NULL for a missing key, a value of another kind, JSON `null`, or a NULL column. `json_has` is false (never NULL) when the key is missing.

## 3.11 Parameters

- A parameter has a declared type and is converted to it, so the database never has to guess.
- `null` after the type allows NULL: `since: date null`. A non-nullable parameter cannot receive NULL.
- A parameter that is declared but never used produces a warning (`QL290`); it still appears in generated code, unused.
- A parameter used several times is bound each time (on MySQL it is listed once per use).
- A string literal given for a uuid, date, timestamp, json or enum parameter is converted and, for enums, checked.

## 3.12 Mutations

```ql
insert add_customer(name: text, email: text null) {
    into customers set name = :name, email = :email
    returning id
}

insert add_orders(cid: int, a: decimal(10,2), b: decimal(10,2)) {
    into orders (customer_id, total) values (:cid, :a), (:cid, :b)
    returning id, status
}

insert copy_paid() {
    into items (order_id, sku, price)
    from orders o join customers c on o.customer_id == c.id
    where o.paid
    select o.id, "copy", o.total
}

update mark_paid(id: int) {
    orders o set paid = true, status = "paid" where o.id == :id
    returning o.id, o.status
}

delete drop_unpaid() {
    from orders o where not o.paid
}

delete clear_notes() {
    from orders o all rows
}
```

- An `insert` takes `set col = value, ...` (one row), or `(columns) values (...), (...)` (several rows), or `(columns) <select>` (rows from a query).
- `update` and `delete` require a `where` condition or the words `all rows`.
- `returning` lists typed result columns (no aggregates); without it the host gets a row count.
- An insert must supply every column that is `not null` with no default and not generated (QL233). `generated always` columns cannot be set (QL234). A column is assigned once (QL235). A NULL cannot be stored in a not-null column (QL232).
- Assignments never narrow (`int` into `smallint` is refused), but integer literals that fit are fine.

**Upserts.** `on conflict` handles a key that already exists:

```ql
insert upsert_category(id: int, name: text) {
    into categories set id = :id, name = :name
    on conflict (id) do update set name = excluded.name
}

insert ensure_category(id: int, name: text) {
    into categories set id = :id, name = :name
    on conflict (id) do nothing
}
```

The conflict target must be the primary key or a `unique` column (QL236). In `do update set`, `excluded` is the row that was refused, and the table's own alias is the existing row.

## 3.13 Result types and nullability

Certo works out, for every result column, its type and whether it can be NULL:

- a schema column is nullable if it is declared nullable;
- a column from the nullable side of a `left join` is nullable;
- an expression is nullable if an operand (a nullable column or `null` parameter) is;
- `sum`, `avg`, `min`, `max` over an empty set are nullable; `count` is never null;
- `case` without `else` is nullable; `coalesce` is not null as soon as one argument is;
- `x is null` is never null.

Generated host code uses this to give you `string?` / `Option<String>` only where NULL can occur.

## 3.14 Fragments

A fragment is a named query used as a table, written once and used in many statements:

```ql
fragment paid_orders() {
    from orders o where o.paid select o.id, o.customer_id, o.total
}

fragment since(cutoff: timestamp) {
    from orders o where o.created >= :cutoff select o.id, o.total
}

query paid_by_customer() {
    from paid_orders p
    join customers c on p.customer_id == c.id
    select c.name, p.total
}

query recent_orders(at: timestamp) {
    from since(:at) r select r.id, r.total
}
```

A fragment is not a database object: each statement that uses one gets it as a `with` query, so there is no migration and nothing to drift. It may use other fragments (not itself), cannot be written to, and takes parameters filled by literals or the statement's own `:params` (never columns). Misuse is `QL260`.

## 3.15 Views (`views.ql`)

A QL view is a query kept in the database as a `CREATE VIEW`:

```ql
view adult_customers { from customers c where c.born < "2008-01-01" select c.id, c.name }

view customer_totals {
    from customers c join orders o on o.customer_id == c.id
    group by c.id, c.name
    select c.id, c.name, sum(o.total) as spent
}

query big_spenders() {
    from customer_totals t where t.spent > 1000 select t.name, t.spent
}
```

Put views in `views.ql` next to `schema.sdl`. `certo migrate apply` creates them in dependency order (a view may read another view); a cycle is `QL262`. Because a view stops a table it reads from being altered, `apply` drops the views before running migrations and creates them again afterwards. A view takes no parameters (use a `query`) and cannot be written to (`QL263`); queries read it like a table.

SDL views (1.9) are the simple, schema-level kind; QL views are the richer kind managed by the runner.

## 3.16 Generated SQL

`certo ql compile` shows the SQL for a dialect:

```text
-- add_task  (?1=title)
INSERT INTO "tasks" AS "tasks" ("title")
VALUES (CAST(?1 AS TEXT))
RETURNING "id" AS "id";
```

Placeholders are `$1`... on PostgreSQL, `?1`... on SQLite and `?` on MySQL. Every identifier is quoted and every parameter is cast to its declared type. The statement's `param_order` says which declared parameter is which placeholder.

# 4. Differences between the databases

Certo makes PostgreSQL, SQLite and MySQL agree wherever it can. What remains:

| Topic | PostgreSQL | SQLite | MySQL 8 |
|-------|-----------|--------|---------|
| Transactions around DDL | A migration is atomic. | Atomic, including table rebuilds. | **Not atomic.** DDL commits as it runs: Certo applies a migration one statement at a time and resumes after a failure. |
| `returning` | Yes | Yes (3.35+) | **No** (QL270): read the row back with a query. |
| Sequences, composite types | Yes | No | No |
| `generated always` | Yes | No | No |
| `text`, `json`, `bytes` in an index or `unique` | Yes | Yes | **No**: use `varchar(n)`. |
| Enums | Enum types | Text with CHECK | Inline `ENUM(...)` |
| Text comparison | Exact | Exact | Exact (tables use the binary collation) |
| `groups` window frames | Yes | Yes | **No** (QL271) |
| `on conflict` | Any unique target | Any unique target | Only where the target is the table's **only** unique key (QL272) |
| `update`/`delete` reading its own table in a subquery | Yes | Yes | **No** (QL273): MySQL error 1093 |
| Foreign key checks | At the end of the statement | At the end of the statement | Row by row (a self-referencing delete of a parent and child in one statement fails) |
| Division by zero in a select | Error | NULL | NULL |
| `string_agg` | `string_agg` | `group_concat` (SQLite 3.44 for `order by`) | `GROUP_CONCAT`; raise `group_concat_max_len` (default cuts at 1024 bytes) |
| Unconstrained `decimal` | arbitrary precision | `NUMERIC` | `DECIMAL(65,30)` |
| NULL ordering in `order by` | NULLs last when ascending | NULLs first | NULLs first |

SQLite stores `uuid`, `timestamp`, `timestamp_naive` and `date` as text, `decimal` as a number or text, and `json` as text. Compare timestamps in the application where the text forms could differ.

# 5. Worked example: from schema to migration

```sdl
enum Status { open, done }

table tasks {
    id: serial primary key
    title: text not null
    status: Status not null default open
}
```

Later you add a column, rename another and drop an enum value. In `schema.sdl`:

```sdl
enum Status { open, done }

table tasks {
    id: serial primary key
    name: text not null
    status: Status not null default open
    priority: int not null default 3
}
```

The diff alone sees `title` dropped and `name` added (destructive). The MDL file says what you meant:

```mdl
rename column tasks.title -> name
```

`certo migrate new rename_title --mdl rename.mdl` then plans: rename the column (data kept), add `priority` with its default. Nothing is destructive.
