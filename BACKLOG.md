HKT is a materially larger change than row polymorphism was: `Ty` today has no notion of a *type constructor* (`F` in `Functor<F<_>>`) as a value distinct from a fully-applied type, so `F<Int>`/`F<Text>` can't even be represented, let alone unified against each other. A real implementation needs: (1) a kind system — at minimum `Type` vs `Type -> Type`, tracked per type-param so `F` can be checked as a 1-arg constructor rather than a concrete type; (2) a `Ty::App(Box<Ty>, Box<Ty>)` (or similar) variant so `F<Int>` is `App(Var(F), Named("Int"))` instead of requiring `F` to already be a concrete `Named`; (3) restricted higher-order unification — full higher-order unification is undecidable in general, but it's tractable here because the only thing ever unified against a kind-`Type -> Type` variable is a *known* constructor (a user's `type Box<T> = ...` or a builtin like `List`), never an arbitrary lambda, so unification can special-case "variable applied to arg" against "known constructor applied to arg" and decompose structurally. None of this can be bolted onto the row-polymorphism post-hoc-check pattern — it has to live in `crates/typeck/src/ty.rs`/`unify.rs` itself, which is why it was scoped out of this session rather than attempted as a partial slice. |
| 120 | Box/unbox a bare type-param value across a generic function's own parameter/return boundary — blocks items 78/79 | Split out of item 119 after actually implementing and testing it (see item 119 in the Completed table above for what shipped: generic records/direct-scope sum-type variants both work end-to-end). The remaining, precise gap: `Secret<T>`/`Permission<T>`'s *required* usage pattern — `priv` constructors can only be called from inside `impl Secret { ... }` (item 74), so external callers must go through factory/accessor methods like `impl<T> Secret { fn wrap(v: T): Secret<T> = Secret(v)  fn expose(s: Secret<T>): T = match s { Secret(v) => v } }` — crosses an *intermediate function call boundary* my item 119 boxing doesn't cover (it only handles direct record-literal/variant-constructor construction and access, not arbitrary function signatures). Confirmed by direct testing, not just theorized: `Secret.wrap(d"19.99")` is a hard C compile error (`passing 'certo_decimal_t' to parameter of incompatible type 'void *'`) since `wrap`'s `v: T` parameter is `void*` in the generated signature but the caller passes a real by-value struct with no boxing inserted at that call site; the equivalent `Secret.wrap(42)`/`Secret.expose(s)` with an `Int` payload *appears* to work (prints the right number) but only via undefined-behavior-adjacent pointer/integer bit-pattern coincidence — `expose`'s `T`-typed return is `void*` in C, an `int64_t` gets implicitly reinterpreted as a pointer on return and reinterpreted back to `int64_t` by the caller, which is not a real fix and would not survive e.g. a stricter compiler or ASan. A real fix needs the same box/unbox decision (declared type is `Ty::Var(_)` ⇒ heap-box) applied to *any* function's parameter passing and return value, not just constructors — bigger surface than item 119's bounded scope (constructors/field access only), since it touches every call site, not a handful of special-cased constructor names. Two real, independent bugs were found and fixed incidentally while investigating this (both now shipped, not blocked): HIR's own `Decl::Impl` lowering had two separate code paths (pre-registration and actual body-lowering) that only scoped a method's own `<U>` type params, never the enclosing `impl<T> { ... }` block's `<T>` — the exact bug item 115 already fixed on the typeck side, but HIR has its own independent lowering pass that never got the fix. Not attempted further this session — same treatment as items 76 (HKT)/116's original scope: a design sketch, not a partial slice, since a half-done version (working for pointer-sized scalars via UB, broken for structs) is worse than not having it, per this item's own Decimal repro. |

| # | Task | Notes |

| 122 | `withTimeout(Duration) { ... }`, supervised `spawn`/`every()` (periodic background jobs) | Split out of item 80 after actually implementing and shipping the other third of it (`Channel<T>` — see item 80 in the Completed table above). `spawn`/`await`/`parallel {}`/`Channel<T>` are all real today, but the runtime has **no task-cancellation mechanism at all** — once `spawn` starts an OS thread, it always runs to completion; there is no cancel-flag, no cooperative check-point, no OS-level thread termination anywhere in the codegen or C runtime. `parallel(timeout:)` (item 81) deliberately sidesteps this rather than solving it: on timeout it panics and *leaks* the thread/handle rather than stopping it, which only works because the process is about to exit anyway. `withTimeout(d) { body }` needs the opposite — the scope's task(s) must actually stop (or at least be abandoned in a way the rest of the program can safely ignore) so execution can *continue* past the timeout, not panic. A real implementation needs, at minimum: (1) a cancellation token/flag threaded through every spawned task's context struct, checked at defined points (loop back-edges? every `await`? — the spec doesn't say); (2) codegen support for inserting those check-points into generated worker functions; (3) `every(Duration) { body }`'s own scheduling loop (a timer thread that re-spawns `body` on each tick) plus "supervision" semantics for `spawn` that spec section 7.3 alludes to (`startBackgroundJobs()`'s example) but never defines precisely (restart on panic? how many times? backoff?). None of this can be bolted onto `Channel<T>`'s mutex/condvar pattern or `parallel(timeout:)`'s leak-and-panic pattern — it needs its own cancellation primitive in `crates/codegen/src/emit_module.rs`'s runtime prelude first, which is why it's scoped out here rather than attempted as a partial slice (a `withTimeout` that doesn't actually stop anything, or an `every()` with unspecified restart behavior, would be worse than not having them, per this project's own standard for items 76/117/118). |
